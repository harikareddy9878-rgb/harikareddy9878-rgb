## Work in four directions

| Direction | Question I explored | Evidence |
| :--- | :--- | ---: |
| Public data | How can twelve separate Telangana health map layers become one reliable analytical view? | 2,628 clean facilities across 33 districts |
| Machine learning | Can a rent estimate reflect locality, size and access without pretending to be exact? | 212 held out Bengaluru examples |
| Language systems | How can a complaint reach a useful queue while uncertain cases remain visible? | 5 routing categories with an abstention rule |
| Software | Can a small electronics store connect stock, payment, delivery, orders and support? | 20 products across 5 categories |

## Project case studies

### 01 · Telangana Public Health Facility Analytics

<table>
  <tr>
    <td width="58%"><a href="https://github.com/harikareddy9878-rgb/telangana-public-health-facility-analytics"><img src="assets/telangana-health-dashboard.png" width="100%" alt="Telangana public health facility dashboard" /></a></td>

### 02 · Bengaluru Rent Estimator

<table>
  <tr>
    <td width="42%" valign="top">
      <p><strong>The issue</strong><br/>A city wide average hides how locality, size, furnishing, property age and metro access interact.</p>
      <p><strong>The build</strong><br/>A repeatable scikit learn pipeline with a held out test set, error analysis and a prediction interval instead of false precision.</p>
      <p><strong>The outcome</strong><br/>The model reached ₹4,677 MAE and 0.816 R² on 212 test examples. The dataset is transparently labelled as a deterministic synthetic sample.</p>
      <p><a href="https://github.com/harikareddy9878-rgb/bengaluru-rent-estimator"><strong>Repository</strong></a> · <a href="https://github.com/harikareddy9878-rgb/bengaluru-rent-estimator/blob/main/reports/Bengaluru_Rent_Estimator_Report.pdf">PDF report</a></p>

### 03 · Consumer Grievance Router India

<table>
  <tr>
    <td width="58%"><a href="https://github.com/harikareddy9878-rgb/consumer-grievance-router-india"><img src="assets/grievance-routing-evaluation.png" width="100%" alt="Consumer grievance routing evaluation" /></a></td>
    <td width="42%" valign="top">
      <p><strong>The issue</strong><br/>People describe the same service problem in different words, while keyword rules can confidently send a complaint to the wrong place.</p>
      <p><strong>The build</strong><br/>An interpretable TF IDF and logistic regression workflow for banking, telecom, travel, ecommerce and appliance complaints.</p>
      <p><strong>The outcome</strong><br/>The router exposes class confidence and uses a 0.62 review threshold. Its 400 examples are synthetic and the project does not submit or decide complaints.</p>
      <p><a href="https://github.com/harikareddy9878-rgb/consumer-grievance-router-india"><strong>Repository</strong></a> · <a href="https://github.com/harikareddy9878-rgb/consumer-grievance-router-india/blob/main/reports/Consumer_Grievance_Router_India_Report.pdf">PDF report</a></p>

## My project standard

I keep source data and transformed data separate, make the main result reproducible, test important rules, state when a dataset is synthetic, include limitations beside the result, and publish visual evidence with a detailed PDF report.
